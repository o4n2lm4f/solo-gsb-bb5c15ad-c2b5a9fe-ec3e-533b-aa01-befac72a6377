# 舞台排练口令同步系统

面向舞台排练场景的口令（Cue）同步 Web 应用。导演编排演出序列，控制端逐条发出口令，仅目标岗位可确认；全部目标确认后才允许推进，超时与重复确认实时标记，断线重连自动恢复现场状态。进行中的口令支持**撤回并纠正重发**（同一序号递增修订号、旧轮次只读封存）。

技术栈：Node.js + Express + WebSocket（`ws`）+ 原生前端（无框架）。

## 快速开始（单条命令）

### 方式一：Docker Compose（推荐）

```bash
docker compose up --build
```

### 方式二：本地 Node.js（≥ 18）

```bash
npm install && npm start
```

启动后通过 **3000 端口** 访问各页面：

| 页面 | 地址 | 用途 |
| --- | --- | --- |
| 首页 / 日志 | <http://localhost:3000/> | 入口导航与本场事件日志 |
| 导演端 | <http://localhost:3000/director.html> | 创建演出序列（序号、口令、目标岗位、确认时限） |
| 控制端 | <http://localhost:3000/control.html> | 开始演出、监控确认状态、临时替岗、撤回纠正重发、推进 / 重置 |
| 岗位端 | <http://localhost:3000/position.html> | 岗位上岗、接收口令、确认 |

> 修改端口：设置环境变量 `PORT`，如 `PORT=8080 npm start`，Compose 中同步调整 `ports` 映射。

## 使用流程

1. **导演端**：逐行填写口令内容与目标岗位（多个岗位用逗号分隔），设置确认时限（秒，3–600），点击「保存序列」。演出进行中序列锁定，需控制端重置后才能修改。
2. **控制端**：点击「开始演出」发出第 1 条口令。页面实时展示每个目标岗位的状态：待确认 / 已确认 / 超时未确认 / 迟到确认，以及岗位在线情况。
3. **岗位端**：输入岗位名「上岗」（岗位名需与序列中的目标岗位完全一致，浏览器会记住）。本岗位是目标岗位时，「确认收到」按钮亮起。
4. **临时替岗**：当前口令尚有未确认目标时，控制端点击该目标旁的「⇄ 替岗」，从**在线且非本条有效目标**的岗位中选择替补并确认。接管后：原岗位立即失去本条确认权（页面划线标注「已由 ×× 接管」），替补岗位端出现「临时替岗」接管提示并可确认，其确认计入全员确认与推进条件；超时未确认标记也随确认权一并移交。替岗**仅对当前轮次生效**，推进到下一条或口令撤回重发后仍使用导演编排的原目标。
5. **撤回并纠正重发**：口令进行中（尚未推进、尚未完成）时，控制端在「撤回并纠正重发」卡片填写**撤回原因**与**修正版口令文本**后点击重发。服务端：
   - 将旧轮次的确认、超时、替岗记录与截止时间**整体封存为只读历史**（保留旧口令文本、旧 revision、旧 attemptId、已确认/超时岗位、撤回原因、封存时间）；
   - 为**同一序号**创建递增修订号（revision 1 → 2 → 3……）与全新 `attemptId`，口令文本替换为修正版，清空本轮确认/超时/替岗状态，**重新开始完整确认时限**；
   - 岗位端确认必须携带其快照中的 `attemptId`；迟到到达的旧轮次确认与旧定时器回调一律**拒绝并写入日志**（`confirm-stale-rejected` / `stale-timeout-rejected`），绝不污染新轮次。
   - 控制端与岗位端实时展示**当前修订号、撤回原因及各旧轮次封存结果**；岗位端收到修订版后需按新口令重新确认。断线重连后凭全量快照恢复一致。**已推进或已完成的口令不可撤回**（服务端拒绝）。
6. **推进**：仅当当前口令**当前轮次**的**全部有效目标**（含替补）都确认后，控制端才能推进到下一条；否则服务端拒绝并提示未确认岗位。
7. **重置**：控制端「重置场次」清空口令进度（事件日志保留），导演端可重新编辑序列。

## 核心规则

- **岗位隔离**：只有当前口令有效目标（原目标或接管后的替补）的岗位端能确认，其他岗位的确认请求被服务端拒绝。
- **临时替岗**：仅控制端可发起，且仅当目标尚未确认；替补必须在线且不是本条有效目标。服务端仅对当前口令原子更新有效目标与确认权限，下一条口令自动恢复导演编排的原目标。替岗的原岗位、替补岗位与发生时间写入事件日志，并随全量状态同步到各端，断线重连后保持一致。
- **状态不串场**：每轮激活时确认表、超时表与替岗表整体重置，上一条（及同一序号已撤回的旧轮次）的确认与替岗绝不带入新一轮。
- **撤回并纠正重发**：仅控制端可发起（`revise`，须含撤回原因与修正版口令文本），且仅对 phase=active 的当前口令生效；已推进、已完成或 idle 状态一律拒绝。旧轮次以只读快照封存到该口令的 `history`（含旧 `attemptId`、revision、文本、确认/超时/替岗、截止时间、撤回原因与封存时间），同一序号 revision 递增并生成新 `attemptId`，重新计时。岗位端 `confirm` 必须携带快照中的 `attemptId`；不匹配或缺失的确认被拒绝并记录（`confirm-stale-rejected`）。旧轮次定时器不被静默取消，而是在原定时点触发后经 `attemptId` 比对拒绝并记录（`stale-timeout-rejected`）。
- **超时标记**：到达确认时限仍未确认的岗位被实时标记为「超时未确认」并写入日志；超时后仍可确认，标记为「迟到确认」。撤回重发后倒计时完全重置。
- **重复确认**：同一岗位对同一条口令的重复确认不改变状态，实时写入日志并标记。
- **断线重连**：岗位端断线后自动重连（1 秒间隔），重连后服务端下发全量状态快照，恢复当前口令、倒计时与本人确认状态；控制端可看到岗位在线 / 离线。
- **事件日志**：本场所有事件（发出口令、确认、迟到、重复、超时、替岗、撤回重发、旧轮次封存、旧确认/旧定时器拒绝、上下线、推进、重置等）保存在内存并追加写入 `data/events-<场次ID>.jsonl`，各页面实时滚动展示。

## WebSocket 协议简述

连接地址：`ws://<host>:3000/ws`

- 客户端 → 服务端：
  - `hello`（登记角色/岗位/clientId）
  - `setSequence`、`start`、`advance`、`reset`
  - `confirm`（岗位端，**必须携带当前快照中的 `attemptId`**：`{ attemptId }`；旧轮次/缺失将被拒绝并记录）
  - `substitute`（控制端指定临时替岗：`{ from, to }`）
  - `revise`（**仅控制端**，撤回并纠正重发当前口令：`{ reason, text }`；仅 phase=active 可用）
- 服务端 → 客户端：
  - `state`（全量状态快照，任何变化即广播，重连恢复依赖于此）。含当前轮次 `attemptId`、当前口令 `currentCue.revision` / `revisionReason` / `history`（各旧轮次只读封存快照：attemptId、revision、旧文本、撤回原因、确认/超时/替岗、截止时间、封存时间、结果），以及顶层 `revision`、`revisionReason`、`substitutions`、`effectiveTargets`
  - `error`（操作拒绝原因，如旧轮次确认被拒、非控制端撤回、已完成口令不可撤回等）
